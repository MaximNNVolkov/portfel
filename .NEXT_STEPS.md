### 6.1. ✅ Секреты и доступ к базе (§28)

- `docker-compose.yml`: убрать публикацию порта `5432:5432` наружу (база должна быть
  доступна только внутри compose-сети), вынести `POSTGRES_PASSWORD` в `.env`.
- `server/token-crypto.ts`: убрать молчаливый fallback на dev-ключ — backend должен
  падать при старте, если `TOKEN_ENCRYPTION_KEY` не задан в production.
- `docs/DEPLOY.md`: в образец `.env` добавить `TOKEN_ENCRYPTION_KEY` и пароль БД —
  сейчас инструкция по деплою их не упоминает, и деплой по ней шифрует токены брокера
  небезопасным ключом.
- **Коммит:** "fix: harden production secrets and database exposure (§28)"

### 6.2. ✅ Настройки портфеля (§13, §6 п.10)

- Эндпоинты `GET/PATCH /api/settings` — поверх уже существующих колонок
  `portfolios.name`/`base_currency` (§11), а не `users.settings` JSONB, как
  предполагалось изначально: решено автономно, чтобы не заводить второй источник
  истины для полей, у которых схема уже даёт первоклассные колонки.
- Базовая валюта (RUB/USD/CNY) и название портфеля связаны с API в `src/AppMvp.tsx`
  (были мёртвые контролы с `defaultValue`); `resolveBaseCurrency`/`engineContext`
  в `server/index.ts` пересчитывают `/api/portfolio/summary`, `/structure`,
  `/recommendations` и снимки истории через выбранную пользователем валюту вместо
  захардкоженного RUB — конвертация в `portfolio-engine.ts` уже была валютно-
  агностична, изменений в самом движке не потребовалось.
- Кнопка «Восстановить демонстрационные данные» убрана из настроек.
- **Коммит:** `a2b26f8` "feat: portfolio settings — base currency and portfolio name (§13)"

### 6.3. Фоновые задачи и планировщик (§32, §19, §21) — блокер

В проекте нет ни одной фоновой задачи, из-за этого:
snapshot портфеля пишется только когда пользователь открывает страницу (§21 требует
ежедневный), синхронизация с брокером — только по кнопке (§19 требует раз в сутки),
котировки обновляются вручную (§20).

- Сервис-планировщик в `docker-compose.yml` (отдельный процесс, как `backup`).
- Ежедневно: snapshot по каждому портфелю, синхронизация подключённых брокеров,
  обновление котировок и курсов ЦБ.
- Ошибки задач — в журнал и в статус интеграции на странице «Интеграции» (§30).
- **Коммит:** "feat: scheduler for daily snapshots, broker sync and quotes (§19/§21)"

### 6.4. Ожидаемые выплаты по вкладам и облигациям (§15, §22) — блокер

Сейчас календарь показывает только выплаты, введённые вручную, и уже прошедшие операции
брокера. §15 требует расчёта процентов по вкладу и формирования будущих выплат,
§22 — типов «возврат тела вклада» и «погашение номинала облигации».

- Генерация плановых выплат из параметров инструмента (ставка, капитализация,
  периодичность, дата окончания; купон, дата купона, погашение).
- Пересчёт при изменении инструмента, без дублей с уже полученными выплатами.
- **Коммит:** "feat: forecast expected payouts for deposits and bonds (§15/§22)"

### 6.5. Асинхронный OCR со статусом (§34)

`POST /api/ocr/upload` выполняет tesseract синхронно в процессе API: запрос на 12 МБ
блокирует обработку остальных. §34 требует асинхронности с отображением статуса.

- Постановка задачи в очередь (тот же планировщик/воркер из 6.3),
  `UploadedDocument.processing_status` уже есть в схеме §11.
- Фронт: страница-сводка опрашивает статус и показывает прогресс.
- **Коммит:** "feat: asynchronous OCR processing with status (§34)"
