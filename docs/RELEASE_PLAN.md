# План вывода в прод для внутреннего тестирования

Документ описывает минимальный путь от текущего состояния до работающего стенда
на VPS, на котором можно проводить внутреннее тестирование. Всё, что не мешает
тестированию, сознательно отложено — точечные доработки вносим по результатам тестов.

Связанные документы: `docs/CLAUDE.md` (правила разработки), `docs/SPEC.md` (ТЗ),
`docs/.NEXT_STEPS.md` (план по этапам 0-6), `docs/DEPLOY.md` (процедура деплоя).

## 2. Блокеры (P0) — без этого на стенд не выкатываемся

Найдены при проверке кода, каждый подтверждён чтением исходников.

### P0-1. ✅ Восстановление из бэкапа не работает поверх существующей базы

`scripts/backup.sh` снимал `pg_dump` без `--clean --if-exists`, а `scripts/restore.sh`
лил дамп через `psql` без `ON_ERROR_STOP`. На пустой базе это сработало бы, на боевой
(а именно так и восстанавливаются) — psql выдал бы «relation already exists», молча
пропустил бы часть команд и оставил базу в смешанном состоянии, отрапортовав успех.
Это прямо ломало критерий приёмки §37 п.17.

- Добавлено `--clean --if-exists` в `pg_dump` (`backup.sh`), `-v ON_ERROR_STOP=1` в `psql`
  и явное интерактивное подтверждение (`CONFIRM=yes` для неинтерактивного запуска)
  в `restore.sh`.
- Проверено реально на временной БД (`postgres_restore_test`, создана и удалена в рамках
  проверки): снят бэкап с тремя строками → база замутирована (изменена строка + добавлена
  новая, итого 4 строки с изменённым значением) → восстановление тем же путём, что и
  `restore.sh` (`psql -v ON_ERROR_STOP=1`, дамп с `--clean --if-exists`) → 0 ошибок,
  данные вернулись ровно к состоянию бэкапа (3 строки, значение восстановлено).
- **Коммит:** "fix: make database restore work against a populated database (§31/§37)"

### P0-2. ✅ OCR в docker-образе остаётся без языковых данных

`server/ocr.ts:143` вызывал `createWorker('rus+eng')`. Файлы `rus.traineddata`
и `eng.traineddata` лежали в корне репозитория, были добавлены в `.gitignore` и не
копировались в образ (`Dockerfile.backend` копировал только `server` и `db`). На сервере
tesseract.js полез бы за ними в интернет при первом распознавании: в лучшем случае
первый скриншот обрабатывается минуты, в худшем (закрытый исходящий трафик) OCR
молча не работает — а это критерий §37 п.5.

- Файлы перенесены в новый каталог `tessdata/` в корне репозитория (остаются
  gitignored — `*.traineddata` в `.gitignore` матчит на любой глубине).
- `Dockerfile.backend`: добавлена строка `COPY tessdata ./tessdata`.
- `server/ocr.ts`: `recognizeText` теперь вызывает `createWorker('rus+eng', undefined,
  { langPath, gzip: false, cacheMethod: 'none' })`. `langPath` вычисляется от расположения
  самого файла (`fileURLToPath(import.meta.url)` → `../tessdata`), а не CWD/абсолютной
  константы — одинаково работает и в dev (`server/ocr.ts` → `../tessdata` в корне
  репозитория), и в образе (`/app/server/ocr.ts` → `/app/tessdata`). `gzip: false` —
  бандл содержит несжатые `.traineddata`, а не `.traineddata.gz` (дефолт библиотеки —
  `gzip: true`, при котором загрузчик искал бы файл с несуществующим расширением).
  `cacheMethod: 'none'` — каждый вызов создаёт и сразу завершает воркер (без пула),
  поэтому кэш между вызовами не даёт выигрыша, а только пишет лишние файлы на диск.
- Проверено, что без этих правок tesseract.js в Node действительно ищет
  `langPath/eng.traineddata.gz` (не `.traineddata`) при `gzip` по умолчанию — прочитан
  `node_modules/tesseract.js/src/worker-script/index.js`.
- **Живая проверка без сети:** сгенерирован тестовый PNG (Python/Pillow) с текстом,
  распознавание запущено через `createWorker` с теми же опциями, что и в `ocr.ts`,
  при `HTTP_PROXY`/`HTTPS_PROXY`, указывающих на заведомо недоступный адрес
  (`http://127.0.0.1:1`) — распознавание прошло успешно, что подтверждает: язык
  реально читается с диска (`langPath`), сеть не требуется даже при `cacheMethod: 'none'`
  (без обращения к локальному кэшу).
- **Проверка образа:** `docker build -f Dockerfile.backend` — собирается чисто;
  `docker run --rm ... ls -la /app/tessdata` подтвердил оба файла (`eng.traineddata`
  5 199 098 байт, `rus.traineddata` 5 053 706 байт) внутри готового образа. Тестовый
  образ и контейнер удалены после проверки (`docker rmi`).
- `npx tsc -b` — чисто.
- **Коммит:** "fix: bundle tesseract language data into the backend image (§18)"

### P0-3. ✅ Rate limiting за nginx считает всех тестировщиков одним клиентом

`server/index.ts` не задаёт `app.set('trust proxy', ...)`, а backend ходит только
через nginx — значит `express-rate-limit` видит один и тот же IP прокси для всех.
Лимит `authLimiter` — 10 попыток входа за 15 минут на всех сразу: несколько
тестировщиков заблокируют друг другу вход в первый же день.

- Сделано при публикации стенда: `app.set('trust proxy', 1)` в `server/index.ts`.
- **Коммит:** "fix: trust nginx proxy so rate limiting keys on the real client IP (§28)"

### P0-4. ✅ Регистрация открыта всему интернету

`POST /api/auth/register` доступен любому, кто знает домен. Для внутреннего теста
на публичном HTTPS это лишняя поверхность: чужой аккаунт на стенде — это чужие
персональные и финансовые данные в нашей базе (§28).

Решение принято автономно (по правилу «резолвим вопросы сами, решение фиксируем
в плане»): вводим код приглашения — переменная `REGISTRATION_INVITE_CODE` в `.env`;
если она задана, регистрация требует совпадающий код, если пуста — работает как
сейчас (нужно для локальной разработки). Это дешевле, чем выключать регистрацию
совсем, и не мешает заводить новых тестировщиков.

- Сделано при публикации стенда: проверка `REGISTRATION_INVITE_CODE` в
  `POST /api/auth/register` плюс поле «Код приглашения» на форме регистрации.
- **Коммит:** "feat: invite code gate for registration on internal test stand (§28)"

### P0-7. ✅ Smoke-тесты API (пункт 6.9)

и парсеры OCR; сквозного теста не было, скрипта `npm test` в `package.json` тоже.

- Сделано: `server/smoke-test.ts` — сквозной сценарий тем же ad-hoc паттерном, что
  и остальные `*.test.ts` (без фреймворка), но с async-вариантом `test()`: регистрация
  пользователя A → вход → добавление позиции → `/api/portfolio/summary` → регистрация
  пользователя B → проверка, что чужие позиции/сводка/прямой доступ по id недоступны →
  удаление аккаунта A → проверка, что токен удалён (401) → самоочистка (удаление B).
  Сам поднимает `server/index.ts` на отдельном порту (`SMOKE_TEST_PORT`, по умолчанию
  3091) поверх текущей `DATABASE_URL`, дожидается `/api/health`, прогоняет сценарий
  через `fetch`, останавливает процесс. Тестовые пользователи удаляют себя сами —
  тест можно гонять повторно (например, перед каждым деплоем), не оставляя мусора в БД.
  Добавлен npm-скрипт `"test": "tsx server/smoke-test.ts"`.
- Найден и исправлен дефект при первой проверке: спавн через `spawn('npx', ['tsx', ...])`
  создаёт цепочку процессов (`npx` → `sh -c` → tsx-обёртка → настоящий node), и
  `SIGTERM`, посланный верхнему `ChildProcess`, до реального процесса не доходит —
  сервер оставался висеть на тестовом порту даже после того, как тест отчитался об
  успехе. Исправлено спавном `tsx` напрямую (`node node_modules/tsx/dist/cli.mjs
  server/index.ts`, без `npx`) — после фикса подтверждено двумя прогонами подряд,
  что порт освобождается сразу после завершения теста.
- **Коммит:** "test: API smoke tests for auth and portfolio flows"

## 3. Выкладка на стенд

**Стенд уже поднят: https://portfel.176.109.108.58.nip.io — описание, эксплуатация
и ограничения в `docs/STAND.md`.** Раздел ниже описывает будущий полноценный
production-деплой через `docker-compose.yml` на выделенный VPS.

После закрытия блокеров — по `docs/DEPLOY.md`, с уточнениями:

1. Подготовить VPS в РФ (§28), поставить Docker и плагин `docker compose` v2.
2. Направить A-запись домена на сервер, открыть 80 и 443.
3. `git clone`, создать `.env`: `POSTGRES_PASSWORD` (`openssl rand -hex 24`),
   `TOKEN_ENCRYPTION_KEY` (`openssl rand -hex 32`), `DATABASE_URL` с тем же паролем
   и хостом `postgres`, `DOMAIN`, `EMAIL`, `REGISTRATION_INVITE_CODE`,
   `TINKOFF_API_MODE=sandbox` на время теста.
4. `docker compose build`, затем `DOMAIN=... EMAIL=... ./init-letsencrypt.sh`,
   затем `docker compose up -d`.
5. Проверить: `docker compose ps` (все сервисы up), `curl https://<домен>/api/health`,
   `docker compose logs backend | head` (миграции применились),
   `docker compose exec backup ls -la /backups` после первого прогона.
6. Завести аккаунты тестировщиков, раздать код приглашения.

Переключение на боевой токен Т-Инвестиций (`TINKOFF_API_MODE=production`) — только
после того, как sandbox-сценарий пройден: до этого момента риск испортить данные
реального брокерского счёта не оправдан.
