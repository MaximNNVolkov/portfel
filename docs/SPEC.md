# Веб-приложение для учёта и анализа инвестиционного портфеля

---

## 0. Приоритизация: MVP v1 vs v2

Документ описывает полную целевую версию продукта. Чтобы не растягивать первый релиз, все функции размечены по приоритету:

- **[MVP]** — обязательно для первого запуска. Без этого продукт не решает основную задачу.
- **[v2]** — важно для полноценного продукта, но не блокирует первый релиз. Разрабатывается после того, как MVP подтвердил свою пользу.

Разметка проставлена по разделам ниже и продублирована в разделе 36 «Этапы разработки».

**Состав MVP v1 (коротко):** портфель, группы инструментов, карточка инструмента, ручной ввод, OCR-добавление по скриншоту, интеграция с Т-Инвестициями, базовый расчёт P&L, календарь выплат (без сложной аналитики), 3-5 правил рекомендаций, авторизация email+пароль, базовая безопасность.

**Вынесено в v2:** PDF-отчёты, административная панель, email/Telegram-уведомления, импорт/экспорт CSV/XLSX, XIRR и исторические курсы валют, несколько портфелей/счетов на пользователя, поддержка брокеров кроме Т-Инвестиций.

## 1. Назначение проекта [MVP]

Веб-приложение предназначено для агрегации, учёта и анализа личного инвестиционного портфеля пользователя.

Приложение объединяет в единую систему:

- банковские вклады;
- ОФЗ;
- корпоративные и муниципальные облигации;
- акции;
- ПИФы и биржевые фонды;
- денежные средства;
- прочие инвестиционные инструменты.

Данные могут поступать из:

1. ручного ввода;
2. загрузки скриншотов с последующим OCR + LLM-анализом;
3. API брокера;
4. импорта CSV/Excel **[v2]**.

**Основная задача:** пользователь не должен вручную сводить информацию из нескольких банковских и брокерских приложений. Система автоматически формирует единую картину портфеля, рассчитывает финансовый результат, показывает будущие выплаты и предоставляет аналитические подсказки.

## 2. Формат приложения [MVP]

- Тип: веб-приложение.
- Размещение: собственный VPS/VDS-сервер.
- Доступ: через браузер по HTTPS.

Требования:

- адаптивная вёрстка;
- полноценная работа на компьютере;
- работа на планшете;
- базовая поддержка мобильного браузера;
- Chrome, Safari, Firefox, Яндекс Браузер.

Приложение не требует установки на устройство.

## 7. Главный экран — «Портфель» [MVP]

Назначение: единая сводная картина всех активов пользователя.

### 7.1. Общие показатели

Отображать:

- общую стоимость портфеля;
- вложено;
- финансовый результат;
- доходность в %;
- полученные выплаты;
- ожидаемые выплаты;
- денежные средства;
- дату и время последнего обновления.

Пример:

```
ПОРТФЕЛЬ
2 350 420 ₽
+184 320 ₽  ·  +8,51%

Инвестировано        2 120 000 ₽
Выплаты получено        94 320 ₽
Ожидается                38 500 ₽
Свободные деньги        136 100 ₽
```

### 7.2. Структура портфеля

Минимальные группы:

- вклады;
- облигации;
- акции;
- ПИФы/фонды;
- денежные средства;
- прочее.

Для каждой группы: вложено, текущая стоимость, P&L в рублях, P&L в процентах, доля портфеля.

Группы должны быть расширяемыми.

### 7.3. Графики

- структура портфеля;
- стоимость портфеля во времени;
- финансовый результат во времени.

Если актуальная цена инструмента отсутствует, явно показывать: *«Актуальная цена недоступна»* или *«Оценка приблизительна»*.

**Никогда не отображать отсутствие цены как стоимость 0.**

Логика пустого/деградированного состояния портфеля — см. раздел 40.1.

## 8. Детализация по группе [MVP]

При выборе группы отображать список инструментов.

Для каждого: название, тикер, ISIN, количество, средняя цена, текущая цена, текущая стоимость, P&L, доходность, дата погашения (если применимо).

**Сортировка:** по стоимости, по доходности, по P&L, по дате погашения.

**Фильтры:** банк, брокер, счёт, валюта, статус.

В верхней части — суммарные показатели группы.

Адаптивное отображение списка (без широких таблиц, пагинация, разворачивание строки) — см. раздел 40.3.

## 9. Карточка инструмента [MVP]

Для каждого инструмента отображать: полное название, тип, тикер, ISIN, эмитент, валюту, количество, сумму вложения, среднюю цену, текущую цену, текущую стоимость, реализованный P&L, нереализованный P&L, полученные выплаты, ожидаемые выплаты, доходность, дату покупки/открытия, дату погашения/оферты, источник данных.

**История:** изменения стоимости, операции, выплаты.

Для данных, введённых вручную или через OCR, разрешить редактирование и удаление.

## 10. Финансовая модель [MVP — базовая логика; XIRR и historical FX — v2]

Это обязательная часть системы. Необходимо разделять:

**10.1. Нереализованный результат** — изменение стоимости активов, которые ещё находятся в портфеле.

**10.2. Реализованный результат** — результат от продажи активов.

**10.3. Полученный доход** — купоны, дивиденды, проценты по вкладам, прочие выплаты.

**10.4. Расходы** — комиссии брокера, комиссии биржи, прочие расходы.

**10.5. Налоги** — учитывать, если доступны из источника данных.

**10.6. Общий финансовый результат.** Базовая логика:

```
изменение стоимости активов
+ полученные выплаты
− комиссии
− налоги
= финансовый результат
```

При пополнениях и выводах денежных средств доходность должна рассчитываться с учётом движения денежных средств.

Для доходности портфеля предусмотреть XIRR **[v2 — на MVP допустима упрощённая формула простой доходности без учёта таймингов пополнений]**.

Методика расчётов должна быть реализована централизованно в Portfolio Engine и не дублироваться на frontend.

## 18. OCR и распознавание скриншотов [MVP]

Пользователь может загрузить один или несколько скриншотов. Система должна уметь распознавать несколько продуктов на одном изображении.

Процесс:

```
Скриншот → OCR → LLM → Структурированные данные
   → Определение типа продукта
   → Поиск существующего инструмента (дедупликация)
   → Сохранение как есть
   → Экран-сводка добавленных записей
```

LLM должен возвращать структурированный JSON. **Подтверждения полей перед сохранением нет** — данные сохраняются как распознаны, без промежуточного шага проверки (см. раздел 40.4). Правка выполняется постфактум, отдельной кнопкой «Редактировать» у каждой записи в экране-сводке.

### Дедупликация

При повторной загрузке система должна искать существующий инструмент по комбинации: название, дата открытия/покупки, дата погашения, сумма, банк/брокер, ISIN/тикер (если доступен).

> **Открытый вопрос перед стартом:** поскольку шага ручного подтверждения перед сохранением больше нет (см. раздел 40.4), нужно решить, как ведёт себя дедупликация при найденном совпадении. Вариант А — система молча создаёт новую запись, а пользователь сам замечает дубликат в экране-сводке и правит/удаляет вручную. Вариант Б — для случая именно дедупликации (не для правки полей) делается единственное исключение и показывается лёгкий inline-выбор «Похожий инструмент уже существует. Обновить или создать новый?» перед сохранением конкретно этой записи. Разработчику стоит выбрать один вариант до старта этапа 2, чтобы не переделывать OCR-флоу.

## 24. Рекомендации [MVP — 3-5 правил ниже]

Рекомендации являются аналитическими уведомлениями и **не являются индивидуальными инвестиционными рекомендациями**.

Правила для MVP:

**Концентрация.** Если инструмент/группа/эмитент занимает более X% портфеля: *«ОФЗ 26238 занимает 31% портфеля»*. Порог по умолчанию: 20–25%, настраиваемый.

**Погашение.** Если крупная позиция погашается в ближайшие N дней: *«Через 23 дня погашается облигация на 350 000 ₽»*.

**Просадка.** Если инструмент показывает значительное снижение: *«Стоимость инструмента снизилась на 12% относительно цены покупки»*. Без рекомендации продавать.

**Выплаты.** Анализировать календарь выплат и выявлять периоды с низкими/нулевыми выплатами.

**Валюта [v2, если исторические курсы ещё не готовы].** Если доля валютных активов превышает заданный порог: *«Доля валютных активов составляет 28%»*.

## 26. PDF-отчёт [v2]

PDF не входит в MVP, но проектируется заранее, так как требует данных, уже присутствующих в системе.

Раздел **«Отчёты»**. Пользователь выбирает: портфель, период, степень детализации. Система формирует PDF на сервере.

**Содержание отчёта:**

1. Титульная страница — название портфеля, период, дата формирования.
2. Общие показатели — стоимость, вложено, финансовый результат, доходность, полученные/ожидаемые выплаты.
3. Структура портфеля — круговая/кольцевая диаграмма.
4. Динамика — график стоимости портфеля.
5. Инструменты — таблица: Инструмент | Кол-во | Стоимость | P&L | Доходность.
6. Выплаты — полученные, ожидаемые, по месяцам.
7. Ближайшие погашения — инструмент, дата, сумма.
8. Аналитические заметки — ключевые особенности портфеля.
9. Дисклеймер — *«Информация носит исключительно информационный характер и не является индивидуальной инвестиционной рекомендацией»*.

PDF должен иметь аккуратный профессиональный дизайн и быть пригоден для сохранения/печати.

## 28. Безопасность [MVP]

Обязательно: HTTPS, хеширование паролей, шифрование чувствительных данных, безопасное хранение токенов, защита API, серверная валидация, защита от SQL injection, XSS, CSRF, rate limiting, журналирование ошибок без секретных данных, резервное копирование БД.

Токены брокеров никогда не записывать в обычные логи.

Пользователь должен иметь возможность удалить свой аккаунт и все связанные данные.

> **Дополнительное требование:** поскольку система хранит персональные и финансовые данные пользователя (в т.ч. токены доступа к брокерским счетам), необходимо явно предусмотреть соответствие 152-ФЗ «О персональных данных» — включая размещение персональных данных граждан РФ на серверах, физически находящихся на территории РФ, если сервис ориентирован на пользователей из РФ. Это стоит зафиксировать как обязательное требование к выбору VPS-провайдера ещё на этапе 0.

## 40. UI/UX-требования (детализация интерфейса)

Раздел уточняет, как именно должны быть устроены ключевые экраны и сценарии, описанные функционально в разделах 6-22. Design system (цвета, шрифты, отступы) в этом ТЗ намеренно не фиксируется — оставлено на усмотрение разработчика (см. 40.6), но структура навигации, состояния экранов и поведение списков — обязательны к исполнению.

### 40.1. Навигация — боковой сайдбар

Основная навигация — фиксированный сайдбар слева.

- На десктопе/планшете: сайдбар всегда виден, с иконкой и подписью для каждого раздела — полный состав пунктов соответствует главному меню из раздела 6: Портфель, Инструменты, Операции, Выплаты, Аналитика, Рекомендации, Отчёты **[v2]**, Интеграции, Импорт **[v2]**, Настройки.
- Активный раздел визуально выделен.
- Внизу сайдбара — блок пользователя (email/аватар) и выход из аккаунта.
- На мобильном экране сайдбар скрывается в выдвижное меню (открывается по кнопке-гамбургеру), но остаётся тем же списком разделов — не заменяется на нижний таббар и не меняет состав пунктов.

Никаких вкладок/табов верхнего уровня, дублирующих сайдбар, не предусмотрено.

### 40.2. Пустой и деградированный портфель

Три возможных состояния экрана «Портфель», в порядке деградации данных:

**A. Портфель полностью пустой (новый пользователь, ни одного инструмента).**
Показывается экран-приглашение, перечисляющий все способы добавления актива, каждый — как отдельная крупная опция с кратким пояснением:

```
Ваш портфель пуст. Добавьте первый актив:

[ 📷 Загрузить скриншот из приложения банка/брокера ]
   Распознаем данные автоматически

[ 🔗 Подключить брокера по API ]
   Т-Инвестиции — данные обновляются автоматически

[ ✍️ Ввести вручную ]
   Если у вас нет скриншота под рукой
```

**B. Есть подключённый брокер, но актуальная синхронизация недоступна (нет связи с API), при этом ранее данные уже загружались.**
Показываем последние сохранённые данные из кэша, с явным баннером над соответствующим блоком/счётом:

```
⚠ Данные от брокера «Т-Инвестиции» по состоянию на 26.08.2026.
Не удалось обновить. [ Повторить попытку ]
```

Баннер крепится к конкретному счёту/брокеру, если брокеров несколько — у каждого своя пометка с датой его последних данных, а не общая для всего портфеля.

**C. Синхронизация недоступна, и кэшированных данных от этого брокера ещё нет вовсе** (первая синхронизация не состоялась), но в портфеле есть другие активы (введённые вручную/через скриншоты).
Показываем ту часть портфеля, которая доступна (ручные + OCR-инструменты + другие подключённые брокеры), и явную пометку:

```
⚠ Не удалось загрузить данные от брокера «Т-Инвестиции».
Показана только доступная часть портфеля.
[ Повторить подключение ]
```

Общая стоимость портфеля на главном экране в состояниях B и C должна визуально помечаться как неполная/по состоянию на дату (не выдавать точную цифру без оговорки).

### 40.3. Списки и таблицы — без широких таблиц

Табличные данные (разделы 8, 22, 23) никогда не отображаются как классическая широкая HTML-таблица с горизонтальным скроллом. Вместо этого:

- **Список карточек/строк**, адаптированный под ширину экрана: на десктопе — компактная строка в 1 линию с ключевыми колонками (название, стоимость, P&L), на мобильном — тот же принцип, но с меньшим числом колонок в свёрнутом виде.
- **Разворачивание строки.** По клику/тапу на строку она разворачивается на месте (аккордеон, без перехода на новую страницу) и показывает 2-3 дополнительные строки деталей (например: количество, средняя цена, дата погашения) — в зависимости от того, сколько деталей помещается по ширине экрана. Повторный клик сворачивает обратно.
- Переход на полноценную отдельную страницу инструмента (раздел 9) выполняется через явный элемент — например, название инструмента как ссылка, или кнопка «Подробнее» внутри развёрнутой строки — а не через сам факт разворачивания.
- **Пагинация.** По умолчанию показываются первые 20 строк. Внизу списка — две отдельные кнопки/контрола:
  - **«Загрузить ещё»** — подгружает следующие 20 строк, добавляя их в конец списка (без перезагрузки страницы).
  - **Выбор количества строк на странице** — переключатель (например, 20 / 50 / 100), меняющий текущий объём загруженных и отображаемых строк.
- Данное поведение (карточный список, разворачивание, пагинация 20+«загрузить ещё») — единый паттерн для всех списков в приложении: инструменты внутри группы, операции, выплаты, распознанные записи со скриншота.

### 40.4. Экран подтверждения после OCR — без правки "на лету"

После обработки одного или нескольких загруженных скриншотов пользователь не редактирует данные в процессе распознавания. Логика:

1. Скриншот(ы) загружены → обработаны OCR/LLM.
2. Все успешно распознанные записи **сохраняются в портфель как есть**, без промежуточного шага подтверждения полей.
3. Пользователю показывается отдельная страница-сводка: **«Добавлено со скриншота от дд.мм.гггг»** — список всех записей, которые были распознаны и добавлены с этой конкретной загрузки.
4. У каждой строки в этом списке — кнопка **«Редактировать»**, ведущая на отдельную страницу редактирования именно этого инструмента (та же форма, что и для ручного ввода), если пользователь хочет что-то поправить или дополнить.
5. Если какой-то файл/фрагмент не удалось распознать — в этом же списке отдельной строкой показывается: *«Не удалось распознать [имя файла]»* с кнопкой **«Добавить вручную»**.

Список из этого экрана не пропадает после ухода со страницы — те же записи попадают в общий список группы инструментов, у каждой сохраняется отметка источника «добавлено со скриншота от дд.мм.гггг» (видна в карточке инструмента, раздел 9).

### 40.5. Форма ручного ввода — пошаговый сценарий

Форма добавления вручную (раздел 17) реализуется как пошаговый визард, а не один длинный экран:

**Шаг 1 — выбор типа инструмента.** Крупные тап-карточки: Вклад / Облигация / Акция / ПИФ / Прочее.

**Шаг 2 — только обязательные поля** для выбранного типа: название, сумма, дата. Ничего лишнего на этом шаге не показывается — цель шага 2 дать пользователю быстро сохранить запись.

**Шаг 3 — подтверждение и сохранение.** Показывается сводка введённых данных и кнопка «Добавить». Опциональные поля (ставка, дата погашения, брокер/банк, тикер/ISIN, валюта, количество) не показываются по умолчанию — доступны через явный элемент **«Добавить дополнительные детали»**, разворачивающий необязательный блок на этом же шаге.

После сохранения — подтверждение с двумя действиями: **«Добавить ещё один актив»** или **«Перейти к портфелю»**.

### 40.6. Design system

Специфика визуального стиля (палитра, типографика, плотность интерфейса, иконки инструментов) в этом ТЗ не фиксируется и оставляется на усмотрение разработчика.

Обязательные ограничения:
- тёмная тема как минимум одним из вариантов темы (по образцу исходных скриншотов пользователя);
- устойчивая цветовая семантика прибыль/убыток — зелёный/красный — единообразно во всём приложении;
- единый набор иконок по типам инструментов (вклад, облигация, акция, ПИФ и т.д.), различимый на карточках и в списках;
- минимальный контраст текста должен соответствовать общим требованиям доступности (WCAG AA).

### 40.7. Модальные окна — не используются

В приложении не используются модальные окна/попапы для содержательных действий. Все сценарии — включая добавление продукта, все шаги формы ручного ввода, редактирование инструмента, экран подтверждения после OCR, подключение/переподключение брокера, настройки — реализуются как **отдельные страницы с собственным URL**, с обычной браузерной навигацией «назад».

Исключение — только служебные системные диалоги браузера (например, нативное окно выбора файла при загрузке скриншота), которые не являются частью UI-слоя приложения.

Для действий, требующих подтверждения (например, удаление инструмента), также используется отдельная страница подтверждения, а не всплывающее окно.
