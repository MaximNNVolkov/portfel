# Деплой на VPS

## Резолюция открытого вопроса о 152-ФЗ (SPEC §38, вопрос №4)

**Хостинг размещается на территории РФ** (решение владельца продукта). Тем самым требование
SPEC §28 о размещении персональных данных граждан РФ на серверах, физически находящихся
в РФ, выполняется по построению — независимо от того, как в дальнейшем будет
квалифицирован состав хранимых данных. Выбор VPS-провайдера ограничен российской
юрисдикцией и площадками в РФ; переносить базу или бэкапы за пределы РФ нельзя.

Практически это значит: сам сервер, том `postgres_data` и каталог с бэкапами
(`postgres_backups`, SPEC §31) остаются в РФ. Если появится внешнее хранилище для бэкапов
или сторонний сервис, получающий данные пользователя, его резидентность нужно проверять
отдельно, а не считать вопрос закрытым навсегда.

Резервное копирование БД (SPEC §31) реализовано — см. раздел «Резервное копирование
и восстановление» ниже.

## Требования

- VPS с Docker и Docker Compose (плагин `docker compose`, не устаревший `docker-compose`).
- Домен, A-запись которого указывает на IP сервера (нужен для настоящего сертификата
  Let's Encrypt — self-signed использовать в проде нельзя, браузер будет ругаться).
- Открытые порты 80 и 443.

## Первый запуск

1. Скопировать репозиторий на сервер.
2. Создать `.env` на основе `.env.example`:
   ```
   PORT=3001
   DATABASE_URL=postgresql://portfel:portfel@postgres:5432/portfel
   SESSION_TTL_DAYS=30
   ```
   Внутри docker-compose backend обращается к базе по имени сервиса `postgres`, а не
   `localhost` — это единственное отличие от локального `.env` для разработки.
3. Собрать образы: `docker compose build`.
4. Получить сертификат Let's Encrypt (одноразовая процедура, решает проблему курицы и яйца:
   nginx не запустится без сертификата, а certbot не может его выдать, пока nginx не отвечает
   на ACME-challenge):
   ```
   DOMAIN=your.domain.com EMAIL=you@example.com ./init-letsencrypt.sh
   ```
   Скрипт создаёт временный самоподписанный сертификат, поднимает `nginx`, запрашивает
   настоящий сертификат у Let's Encrypt через webroot-плагin, подменяет сертификат и
   перезагружает `nginx` без даунтайма.
5. Поднять остальной стек:
   ```
   DOMAIN=your.domain.com docker compose up -d
   ```
   `postgres` и `backend` запускаются автоматически; SQL-миграции (`db/migrations/*.sql`)
   применяются самим backend-процессом при старте (`runMigrations`, см. `server/index.ts`) —
   отдельного шага `db:migrate` для докер-деплоя не требуется.
6. Сервис `certbot` продолжает работать в фоне и обновляет сертификат каждые 12 часов
   (`certbot renew` — no-op, если срок действия сертификата ещё не подходит к концу).

## Обновление после первого запуска

```
git pull
docker compose build
docker compose up -d
```

Сертификат перевыпускать не нужно — том `./certbot/conf` сохраняется между перезапусками.

## Резервное копирование и восстановление (SPEC §31)

Отдельный сервис `backup` в `docker-compose.yml` (образ `postgres:16-alpine`, в котором уже
есть `pg_dump`/`psql`) работает бесконечным циклом — по тому же паттерну, что и цикл обновления
сертификата в сервисе `certbot`:

- раз в сутки (`BACKUP_INTERVAL_SECONDS`, по умолчанию 86400) снимает `pg_dump` всей базы,
  сжимает `gzip` и кладёт в именованный том `postgres_backups` (`/backups` внутри контейнера)
  как `portfel-<UTC-дата>-<UTC-время>.sql.gz`;
- хранит только `BACKUP_RETENTION_COUNT` (по умолчанию 7) самых свежих копий — более старые
  файлы удаляются автоматически после каждого нового бэкапа.

Сам скрипт — `scripts/backup.sh`, монтируется в контейнер `backup` только на чтение
(правки скрипта не требуют пересборки образа, достаточно перезапустить контейнер).

**Посмотреть список бэкапов:**
```
docker compose exec backup ls -la /backups
```

**Восстановить базу из конкретного бэкапа** (`scripts/restore.sh`, тоже примонтирован
в контейнер `backup`):
```
docker compose exec backup sh /restore.sh /backups/portfel-20260912-030000.sql.gz
```
Восстановление накатывает дамп поверх уже существующей базы — перед восстановлением
на боевые данные стоит убедиться, что это осознанное действие (например, что backend
на это время можно остановить, чтобы он не писал в базу параллельно с восстановлением).

Восстановление проверено в разработке: `pg_dump` реальной dev-базы → `gzip` → восстановление
дампа в отдельную временную базу через `psql` → сверено количество таблиц в схеме `portfolio`
до и после (совпало) → временная база удалена.

## Ограничения этого окружения

Из песочницы агента невозможно проверить полноценный прогон с реальным доменом, DNS
и выданным сертификатом Let's Encrypt — это требует внешнего VPS с публичным IP. Проверено
только: `docker compose build` для `backend`/`nginx` (образы собираются без ошибок) и вся
логика приложения — через локальный e2e с curl против `tsx server/index.ts` и Postgres.
