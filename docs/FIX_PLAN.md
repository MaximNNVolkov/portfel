### 1.1. BUG-01 — backend не поднимается сам, стенд отдаёт 502 · L — ✅ Готово

Стенд был поднят вручную (`npm run api` + `npm run scheduler`), supervisor'а не было:
после перезагрузки VPS или падения процесса весь API отдавал 502. Воспроизводилось
дважды за два прогона. Это же корень BUG-24 (бэкапы) и половина BUG-10 (воркер
не поднимается после падения).

**Выбран путь systemd, а не `docker compose up -d`.** Причины: (1) на сервере нет
плагина `docker compose` v2, только сломанный устаревший `docker-compose` v1
(см. предыдущие пункты плана разработки, где это уже фиксировалось); (2) Postgres
стенда — нативный `postgresql.service`, а не контейнер, поэтому переезд на compose
означал бы риск миграции данных ради самого этого фикса; (3) systemd на сервере
уже используется (nginx, postgresql), полностью рабочий.

Ранее `docs/STAND.md` утверждал, что установка systemd-юнитов «заблокирована
политикой окружения» — проверено эмпирически безопасным пробным юнитом
(`oneshot`, `/bin/true`): `sudo systemctl daemon-reload`/`start`/`disable` прошли
без единого отказа. Блокировки не оказалось.

Установлены `/etc/systemd/system/portfel-api.service` и
`/etc/systemd/system/portfel-scheduler.service` (`Restart=always`,
`WantedBy=multi-user.target`, `enabled`), логи — `/var/log/portfel/{api,scheduler}.log`.
Старые голые `tsx`-процессы остановлены, сервис переведён на юниты без ощутимого
простоя. Проверено: `sudo systemctl restart` — поднимается штатно; `kill -9` на PID
API — systemd респавнит процесс за секунды, публичный HTTPS-домен снова отвечает.
Полный `reboot` общего VPS не выполнялся намеренно — на машине есть чужие сервисы
(`bonds.*`, `expedition.*`), настоящая перезагрузка — риск для них, требующий
отдельного согласия владельца; respawn после `kill -9` покрывает то же свойство
(автоматическое восстановление без ручных действий), не трогая остальные сервисы.

Путь зафиксирован в `docs/STAND.md` (разделы «Как устроено», «Эксплуатация»,
«Ограничения») — `docs/DEPLOY.md` не трогался, он описывает отдельный,
ещё не развёрнутый compose-путь на будущем выделенном VPS, а не этот стенд.

**Коммит:** `ops: run the stand under a supervisor so the API survives restarts (§30)`

### 1.2. BUG-10 — битая картинка роняет OCR-воркер целиком · M — ✅ Готово

`server/scheduler.ts:ocrLoop` уже ловит ошибки через `.catch`, но tesseract.js
бросает исключение из обработчика события — `process.nextTick(() => { throw err })`,
мимо `await`. Процесс падает с кодом 1, и OCR встаёт у всех пользователей;
в UI это вечное «В очереди на распознавание…» без ошибки и без отмены.

Реализовано (все 4 подпункта):

1. `server/ocr.ts:recognizeText` — `worker.recognize` обёрнут в try/catch,
   `worker.terminate()` гарантирован в `finally`, документ помечается `failed`
   с понятной причиной.
2. `server/scheduler.ts` — добавлены `process.on('uncaughtException')` /
   `unhandledRejection`: логируют и не останавливают цикл.
3. Добавлен таймаут обработки: миграция `006_ocr_claim_timeout.sql` (колонка
   `claimed_at` + частичный индекс), `failStaleProcessingDocuments` в
   `server/repository.ts` переводит документы, зависшие в `processing` дольше
   `OCR_STALE_TIMEOUT_MINUTES` (по умолчанию 5 мин), в `failed`; вызывается из
   `staleDocumentLoop` в `server/scheduler.ts` каждые `OCR_STALE_CHECK_SECONDS`
   (по умолчанию 60 с).
4. `src/AppMvp.tsx` — кнопка «Попробовать ещё раз» на экране загрузки скриншота
   при ошибке.

Код фактически landed раньше (коммит `7ea7ee5`, автоматический
`chore: safety commit`), этот раунд — верификация на живом стенде и закрытие
пункта в плане.

**Проверено на живом стенде** (не только код): применена миграция 006 через
рестарт `portfel-api.service`/`portfel-scheduler.service` (`Applied migration
006_ocr_claim_timeout` в `api.log`, колонка и частичный индекс подтверждены
`\d portfolio.uploaded_documents`). Живой e2e: вручную вставлен документ со
статусом `processing` и `claimed_at` на 10 минут в прошлом → в течение одного
цикла `staleDocumentLoop` строка перешла в `failed` с сообщением «Обработка
изображения заняла слишком много времени» — подтверждает, что зависший
документ больше не блокирует очередь навсегда. Тестовая строка удалена из БД
после проверки. Устойчивость к необработанным ошибкам подтверждена косвенно:
до применения миграции сервис уже жил через ошибки `column "claimed_at" does
not exist` в `scheduler.ocr`/`scheduler.ocr-stale` без падения процесса
(`daily run: done` отработал следом же). `npx tsx server/ocr.test.ts` (14/14) и
`npx tsc -b` — чисто. Фронтенд с кнопкой «Попробовать ещё раз» пересобран и
выложен на `/var/www/portfel/`.

**Коммит:** `fix: isolate OCR failures so one broken image cannot kill the worker (§18/§34)`

### 1.3. BUG-24 — на стенде никто не снимает бэкапы · S — ✅ Готово

Прямое следствие 1.1: сервис `backup` — часть compose-стека, а стенд поднят голыми
процессами (затем — systemd-юнитами, 1.1), поэтому `/backups` не существовал вовсе.
Скрипты рабочие (проверены в P0-1), но восстанавливать было нечего.

Путь systemd (не compose) уже выбран в 1.1, поэтому реализован именно вариант из
плана: cron-джоб на `scripts/backup.sh` с постоянным каталогом.

**Реализовано:**

1. `scripts/backup.sh` — добавлен режим `RUN_ONCE=1`: скрипт делает один прогон
   `run_backup` и завершается, вместо бесконечного цикла `while :; do ...; sleep;
   done`. Бесконечный цикл был рассчитан на постоянно работающий контейнер
   docker-compose, где периодичность держит сам процесс; для cron периодичность уже
   задаёт планировщик ОС — держать процесс живым сутками между запусками было бы и
   не нужно, и не соответствовало бы модели systemd/cron, принятой в 1.1.
2. Каталог `/home/user1/portfel-backups` (права `700`, только владелец) — постоянное
   хранилище дампов на стенде, не временный путь.
3. Джоб в пользовательском `crontab` (тот же механизм, что уже используется на этой
   машине для других проектов — `crontab -l` показывает `futures`/`cmc_bot` джобы,
   не только root-cron):
   `11 3 * * * PGHOST=localhost PGUSER=portfel PGPASSWORD=portfel PGDATABASE=portfel
   BACKUP_DIR=/home/user1/portfel-backups RUN_ONCE=1 /bin/sh
   /home/user1/portfel/scripts/backup.sh >> /home/user1/portfel-backups/backup.log 2>&1`.
   Учётные данные совпадают с `DATABASE_URL` из `.env` стенда (`postgresql://portfel:
   portfel@localhost:5432/portfel`) — тот же `pg_dump --clean --if-exists` из
   `scripts/backup.sh`, restore — та же уже проверенная в P0-1 процедура
   `scripts/restore.sh`.

**Проверено на живом стенде:** ручной прогон именно той команды, что стоит в cron
(`RUN_ONCE=1 sh scripts/backup.sh`), дал валидный `portfel-20260925-141347.sql.gz`
в `/home/user1/portfel-backups` (`gzip -t` прошёл, `zcat | head` показал корректный
заголовок `pg_dump`). Строка появилась и в `backup.log`. Ждать реальных суток для
формальной проверки критерия приёмки не требовалось — критерий («хотя бы один файл
в каталоге») уже выполнен этим прогоном, а cron гарантирует появление новых файлов
ежедневно в 03:11 без дальнейшего вмешательства; retention (`BACKUP_RETENTION_COUNT`,
по умолчанию 7) и сама логика `--clean --if-exists`/восстановления уже были проверены
ранее в пункте P0-1 плана `docs/RELEASE_PLAN.md` и не менялись в этом пункте.
`npx tsc -b` — чисто (правки только в shell-скрипте и cron, TypeScript не затронут).

**Коммит:** `ops: make the stand actually take daily database backups (§31/§37)`

### 2.2. BUG-17 — список и карточка считают стоимость по цене покупки · M — ✅ Готово

`server/positions.ts:166` отдаёт `amount: position.value` — сохранённое при вводе
значение, тогда как `/api/portfolio/summary` и `/api/portfolio/structure` считают
через `server/portfolio-engine.ts:149` (`quantity × currentPrice`). Отсюда акция
на трёх экранах стоит 31 000 ₽, а на двух — 28 000 ₽ с «+0,0%», и сортировки
«по стоимости»/«по P&L» в списке сортируют по неверным числам.

Это ровно то, что запрещает CLAUDE.md: расчёт продублирован мимо Portfolio Engine.
`GET /api/positions` должен отдавать оценку движка — `valueBase`, `pnl`, `pnlPercent`,
`priceUnavailable` — а не сырое поле из БД. Фронт после этого перестаёт считать
`product.amount - product.invested` (`src/AppMvp.tsx:1542`, `1624`, `2128`) и берёт
готовые поля.

**Коммит:** `fix: value positions through the portfolio engine everywhere (§10)`

Сделано: `server/positions.ts:positionToWire` принимает оценку движка и отдаёт её
вложенным объектом `valuation` (`value` = `valueBase`, `invested` = `investedBase`, `pnl`,
`pnlPercent`, `priceUnavailable`, `priceUnavailableReason`) — ровно тот же
`evaluatePosition(toEngineInput(position))`, по которому считаются `/api/portfolio/summary`
и `/structure`. В `server/index.ts` все четыре ответа с позицией (`GET /api/positions`,
`GET /api/positions/:id`, `POST`, `PATCH`) идут через общий `valuedPositions`. Сырое
`amount` осталось в ответе как введённое пользователем значение — его читает форма
редактирования, на экранах стоимости оно больше не используется.
Фронт (`src/AppMvp.tsx`): `pnlDisplay(pnl, pnlPercent)` только форматирует готовые числа
движка (и печатает «—» для `null`, §7.3), `valuationOf(product)` берёт `valuation` из ответа;
пересчёт `amount − invested` остался только в офлайн-фолбэке без бэкенда, по тому же
принципу, что и `localSummary`. Переведены: строка списка «Инструменты», карточка
инструмента («Текущая стоимость», «Нереализованный P&L»), страница удаления, сортировки
«по стоимости / доходности / P&L» (позиции без оценки уходят в конец, а не сортируются
как нулевые), разрезы структуры (§23 — берут `pnl`/`pnlPercent` из `aggregateByKey`).
После OCR список позиций перечитывается с бэкенда, а не дополняется снимком из результата
распознавания, у которого оценки нет.

Проверено: `npx tsc -b`, `npm run build`, все `server/*.test.ts` — чисто. В
`server/smoke-test.ts` добавлен регрессионный сценарий ровно из отчёта: акция 10 шт.,
средняя 2 800, текущая 3 100, введённая сумма 28 000 → `POST`, `GET /api/positions` и
`GET /api/positions/:id` отдают `valuation.value = 31 000` и `pnl = 3 000`, а сводка —
`total`, включающий те же 31 000. Прогон зелёный.

### 2.3. BUG-15 + BUG-12 — OCR задваивает портфель и заводит «Итого» активом · L — ✅ Готово

Две беды одного конвейера, чинятся вместе, иначе проверить нечего.

**BUG-15.** Повторная загрузка того же файла каждый раз создаёт полный комплект
записей: 4 прогона дали 22 позиции и «Общая стоимость ₽ 4 774 540» вместо ~533 тыс.
Дедупликация по имени+сумме (`server/ocr.ts:193-194`) только помечает флагом
`possibleDuplicate` и ничего не блокирует. Вариант А из SPEC §18 («молча создавать»)
принимался для похожих инструментов, а не для побайтово того же файла.

Добавить хеш содержимого файла в `uploaded_documents`; при совпадении — не обрабатывать
повторно, а показать экран-сводку прошлой обработки с пометкой «этот скриншот уже
загружался дд.мм.гггг». Это не inline-модалка, запрета §40.4 не нарушает.

**BUG-12.** Парсер (`server/ocr.ts:buildOcrCandidates`) режет текст построчно и
заводит активом всё, где есть число: строка «Итого: 533 698,50 ₽» стала пятым активом
и удвоила портфель, а название «ОФЗ» и её цифры «120 шт · 567,30 ₽ · 68 076 ₽»
разъехались по разным записям.

1. Чёрный список итоговых строк: `Итого`, `Всего`, `Баланс`, `Total`, `Сумма портфеля`.
2. Склейка строки-названия со следующей строкой количества/цены, когда в первой
   нет суммы, а во второй нет названия.
3. Не принимать номер выпуска облигации за сумму (`ОФЗ 26238` → 26 238 ₽ сейчас
   проходит как сумма) — если в строке распознан тикер/номер выпуска, число из него
   исключается из кандидатов на сумму.

Всё это — чистые функции, покрываются `server/ocr.test.ts` на синтетическом тексте,
без картинок.

**Коммиты:** `fix: skip screenshots that were already processed (§18)` и
`fix: stop the screenshot parser from turning totals into assets (§18)`

Сделано — **BUG-15** (коммит `f03b790`): миграция `007_ocr_content_hash.sql` — колонка
`content_hash` (SHA-256 содержимого файла) и индекс `(user_id, content_hash)`.
`POST /api/ocr/upload` считает хеш и через `findProcessedDocumentByHash`
(`server/repository.ts`) ищет прошлую загрузку того же пользователя: в очереди, в работе
или обработанную, от которой в портфеле осталась хотя бы одна позиция. Найдена — новый
файл удаляется с диска, ответ `200 {documentId: <прошлый>, alreadyUploadedAt}`; фронт
опрашивает прошлый документ как обычно и показывает его сводку с баннером «Этот скриншот
уже загружался дд.мм.гггг — повторно он не обрабатывался, новые записи не созданы».
Упавшие обработки и файлы, все записи которых пользователь уже удалил, не блокируют
повторную загрузку — иначе исправить неудачное распознавание было бы нельзя. Попутно:
удаление аккаунта (§28) теперь стирает и ещё не обработанные файлы загрузок с диска,
а не только строки в БД. Проверено: `server/smoke-test.ts` — две загрузки одного PNG
подряд дают `202` и `200` с тем же `documentId` и `alreadyUploadedAt`.

**BUG-12**: в `server/ocr.ts` — `isTotalLine` (чёрный список «Итого / Всего / Баланс /
Total / Сумма портфеля» в начале строки; «Итоговая доходность», «Вклад Итоговый» не
задеваются), `stripIdentifiers` (номер выпуска ОФЗ/ОФЗ-ПД, ISIN, «№ N» исключаются из

«Р»/«P» вместо «₽» названием не считаются). Итоговые строки убраны и из запасного разбора
всего текста, иначе одинокое «Итого: …» вернулось бы через него.
Проверено: в `server/ocr.test.ts` +5 тестов, главный — текст скриншота ровно из отчёта
(вклад 450 000, «ОФЗ 26238» / «120 шт · 567,30 Р · 68 076,00 Р», «SBER» / «50 шт

### 2.4. BUG-05 — пополнение не попадает в «Свободные деньги» · M — ✅ Готово

Транзакция `DEPOSIT` 500 000 ₽ видна только в списке операций: сводка её не учитывает
(`/api/portfolio/summary` агрегирует позиции и ничего не знает о денежном остатке),
а фронт берёт «Свободные деньги» из позиции типа «Деньги» (`src/AppMvp.tsx:1408-1414`),
которой никто не создаёт. Пользователь, который завёл деньги и ещё не купил бумаг,
видит пустой портфель.

SPEC §12 требует считать денежные остатки частью портфеля. Считать остаток на бэкенде
из транзакций (`DEPOSIT` + продажи + выплаты − `WITHDRAW` − покупки − комиссии − налоги),
отдавать отдельным полем `cash` в `/api/portfolio/summary`, включать в общую стоимость
и в структуру как группу «Денежные средства».

Решение принято автономно (Р-2 ниже): вариант А — остаток считается частью портфеля.

**Коммит:** `feat: count cash balances as part of the portfolio (§12)`

Сделано: `server/repository.ts:sumCashBalances` — сальдо по валютам ровно по формуле
плана (`DEPOSIT` + `SELL` + купоны/дивиденды/проценты/погашения − `WITHDRAW` − `BUY` −
`FEE`/`TAX` − поля `commission`/`tax`). `server/daily-tasks.ts:portfolioEngineInputs`
добавляет остаток в вход Portfolio Engine позицией «Денежные средства» группы «Деньги»
(по одной на валюту, вложено = остатку, чтобы деньги не давали P&L — доход, ставший
деньгами, уже учтён как полученные выплаты §10.3). Через неё теперь считаются сводка,
структура (§23: разрезы «по валютам» и «по инструментам»; брокер/банк/эмитент — нет),
рекомендации (доли — от всего портфеля) и ежедневные снимки истории (§21; снимок
пишется и для портфеля из одних денег). `/api/portfolio/summary` отдаёт поле `cash`
(`null`, если курса валюты остатка нет — не ноль, §7.3). Фронт берёт «Свободные деньги»
из `summary.cash`, а портфель из одних денег больше не показывается пустым.
Старый механизм «сдвигать сумму позиции типа „Деньги“ при денежной операции» удалён:
такую позицию никто не создавал (в этом и был BUG-05), а при остатке из операций он
посчитал бы пополнение дважды.

Решено автономно (дополнительно к Р-2): (1) брокерские операции в сальдо не входят —
состояние брокерского счёта целиком приходит из его позиций при синхронизации, иначе
деньги посчитались бы дважды; (2) отрицательное сальдо (покупки записаны, пополнения —
нет) в портфель не попадает — такие покупки оплачены деньгами, о которых система не
знает, и «минус» уменьшил бы стоимость на сумму, которую пользователь никому не должен.

Проверено: `npx tsc -b`, `npm run build`, все `server/*.test.ts`; в smoke-тест добавлен
сценарий: пополнение 500 000 при позиции 100 000 → `cash = 500 000`, `total = 600 000`,
в `groups` есть «Деньги» 500 000; покупка 50 000 → `cash = 450 000`, `total` не изменился
(деньги переложены в бумагу, а не удвоены); удаление обеих операций → `cash = 0`,
`total = 100 000`. Прогон зелёный.

### 2.7. BUG-20 — по облигации нет купонов без «Даты выплаты купона» · M — ✅ Готово

разделе «Выплаты» со ссылкой «Заполнить» на страницу правки — вместо молчаливого нуля.

### 2.8. Замечание 20 — вклад с истёкшим сроком выпадает из календаря · M — ✅ Готово

Вклад 500 000 ₽ под 16% с датой окончания 01.09.2026 не дал ни процентов, ни возврата

потеря 20 000 ₽ процентов и 500 000 ₽ возврата тела.

Снять фильтр по «сегодня» в `forecastDeposit`: прогноз строится на весь срок вклада,

с будущими и завысят «Ожидается». Покрывается `server/payout-forecast.test.ts`.

**Коммит:** `fix: forecast payouts for deposits whose term has already ended (§15)`

Сделано: `server/payout-forecast.ts:forecastDeposit` больше не отбрасывает периоды по
«сегодня» — прогноз строится на весь срок от даты открытия позиции (раньше неё не
уходит), прошедшие проценты и возврат тела приходят со статусом `expected`, и благодаря
2.6 бэкенд помечает их `overdue`: в календаре они стоят в «Просрочено», в «Ожидается» не
складываются. Ручные/полученные строки на те же даты прогноз, как и раньше, не

Побочный эффект, учтённый в интерфейсе: у вклада, заведённого задним числом с

добавлены пагинация по общему паттерну §40.3 и кнопка «Отметить все полученными (N)».
После выкладки на стенд ближайший пересчёт прогноза сразу выведет такие прошедшие
выплаты для уже заведённых вкладов — это ожидаемое поведение по решению Р-1.

Проверено: `server/payout-forecast.test.ts` — прежний тест «прошедшие периоды в прогноз
не попадают» заменён противоположным (15 ежемесячных выплат за весь срок, ни одной
раньше открытия) и добавлен случай из отчёта: 500 000 ₽ под 16% до 01.09.2026 → проценты

## Решения, принятые автономно

Оба вопроса, всплывшие при разборе отчёта, решены здесь же — по действующему в проекте
правилу простой обратимый выбор делается сразу, а не ждёт ответа. Если решение окажется
неверным, его меняем отдельным пунктом.

### Р-1. Вклад с истёкшим сроком (Замечание 20)

решено автономно: показывать ли выплаты по вкладу, срок которого уже закончился →
да, генерировать их со статусом «Ожидается» и датой в прошлом, чтобы пользователь
отметил полученными; вклад при этом остаётся активным → альтернативы хуже: закрывать
вклад автоматически — значит молча убрать из портфеля 500 000 ₽, которые человек
физически ещё не получил, а объяснительная надпись «прогноза нет» оставляет его без
суммы, которую он вправе ожидать (§7.3 запрещает и ноль, и умолчание). Вариант
с прошедшими выплатами вдобавок не требует отдельного механизма: он ложится
в группу «Просрочено» из 2.6. Реализация — пункт 2.8.

### Р-2. Что считать «свободными деньгами» (BUG-05)

решено автономно: считать ли непотраченные пополнения частью портфеля →
да, свободные деньги = сальдо денежных движений, входят в общую стоимость и в структуру
отдельной группой «Денежные средства» → §12 прямо называет денежные остатки частью
портфеля, а §7.1 требует строку «Свободные деньги» в сводке; трактовка «пополнение —
только запись в истории» расходится с ТЗ и оставляет на главном экране цифру, которая
никогда не заполнится. Реализация — пункт 2.4.

## Чего в плане сознательно нет

- **Safari** (§37 п.16) — в среде тестировщика недоступен физически, не проверен
  ни разу. Нужен отдельный прогон на macOS/iOS перед раздачей доступа; в план
  доработок это не входит, но из критериев приёмки не выпадает.
- **Сквозная проверка синхронизации Т-Инвестиций** — прогон 2 подтвердил только
  пути «токена нет» и «токен неверный»; путь с валидным sandbox-токеном
  и непустым портфелем живьём не пройден.
- **Правила рекомендаций кроме `concentration`** — `maturity`, `drawdown`,
  `payout_gap` подтверждены чтением кода и юнит-тестами, но не сценарием на стенде.

Это не найденные дефекты, а непокрытые области. Добавить их в чек-лист следующего прогона.
